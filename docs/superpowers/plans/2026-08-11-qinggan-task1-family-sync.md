# 青甘随行 Task 1 — Execution State, Family Identity & Device Sync Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** 把现有只读青甘行程升级为可由爸爸 / 妈妈 / 姐姐 / 弟弟 / 爷爷 / 奶奶六个家庭身份在独立 iPhone 上共同执行、单设备绑定、弱网 local-first、正常网络 0–10 秒级自动同步的旅行执行系统。

**Architecture:** 保持现有 itinerary 计划事实不变，新增 Family Binding 与 Trip Execution 两组独立运行时事实。服务器使用 Spring Boot + MySQL 作为执行状态权威源；iOS 使用 Keychain 保存家庭/设备凭据，Application Support 保存 execution snapshot + pending actions，并采用前台 10 秒 polling、回前台立即刷新、写后采用服务端响应、网络恢复 `binding validation → pull → reconcile → flush → pull` 的同步策略。

**Tech Stack:** Java 17, Spring Boot 3.5.7, Spring Web, Spring Data JPA, Flyway, MySQL 8.x, H2 test profile, Testcontainers 1.21.4, Swift 6, SwiftUI, Observation, Foundation, Security/Keychain, Network.framework, XCTest, iOS 17+.

**Recommended Codex execution:** strongest coding model available; preferred GPT-5.6 Luma when selectable. **Reasoning: High.**

## Global Constraints

- Existing Xcode project must be modified in place; never create a second iOS app project.
- Task 0 Production Runtime Foundation is a hard dependency and must remain green.
- Production API base remains `https://qinggan.findagent.tech`; Debug may override with localhost.
- All new backend routes use the existing project convention `/api/v1/trips/...`. The Design Spec examples that omitted `/v1` are normalized here to match the existing `ItineraryController` contract; this is an API consistency correction, not a product-scope change.
- Do not modify the itinerary endpoint into a mutable aggregate. Keep `GET itinerary`, family binding resources, execution snapshot, and execution mutations separate.
- Do not add WebSocket or SSE.
- Do not add background polling, background location, family live-location sharing, push notifications, MapKit, weather, or photo check-in in Task 1.
- App foreground polling interval is exactly 10 seconds in production.
- App background/inactive state must cancel foreground polling.
- App returning to active state must refresh immediately.
- Network recovery order is exactly: validate active device binding → pull latest execution snapshot → reconcile pending → flush pending in creation order → final pull.
- Six stable role codes are: `FATHER`, `MOTHER`, `OLDER_SISTER`, `YOUNGER_BROTHER`, `GRANDFATHER`, `GRANDMOTHER`.
- One role may have at most one ACTIVE device in one Trip; one device may have at most one ACTIVE role in one Trip.
- V1 roles have equal execution permissions; role is identity/audit ownership, not an authorization hierarchy.
- `Family Join Token` is only for roles/bind/takeover. Normal execution uses a per-binding `Device Token`.
- Family Join Token and Device Token must never be committed as production plaintext, included in URL query strings, or printed in logs.
- Production Compose must require server-side `QINGGAN_FAMILY_JOIN_TOKEN` and `QINGGAN_DEVICE_TOKEN_SIGNING_SECRET` environment variables.
- Device Token plaintext is returned over HTTPS and stored in iOS Keychain; backend persists only its SHA-256 hash.
- Device-token issuance must remain idempotent without storing plaintext: use deterministic HMAC-SHA256 output keyed by `QINGGAN_DEVICE_TOKEN_SIGNING_SECRET` over binding identity inputs, then persist only SHA-256(token).
- A takeover must atomically REVOKE the old device and activate the new device.
- Old-device pending actions must never be automatically submitted after the binding has been revoked.
- Actor `role`, `deviceId`, and `bindingVersion` are derived from authenticated Device Token context; never trust client-supplied actor identity.
- `actualStartDate` is generated by the backend from the server-applied instant interpreted in the Trip `timeZone`; client `occurredAt` is audit-only.
- Existing `trip.actual_start_date` and `trip.status` remain a compatibility mirror for the itinerary response. `trip_execution` is the runtime execution authority; start writes both inside one transaction.
- Execution revision is separate from itinerary `trip.revision`.
- Stop execution rows are sparse overrides. Effective status is `execution override ?? plan stop.status`.
- `completed` and `skipped` are resolved; only `completed` counts as completed. Origin does not count in progress. `moved` is not nextStop.
- Allowed stop transitions: `planned→arrived`, `planned→completed`, optional `planned→skipped`, `arrived→completed`, optional `arrived→skipped`, optional `skipped→completed`.
- Forbidden: completed regression, skipped→planned, required skip, direct user-set moved.
- Every mutation uses UUID `requestId`; `(tripId, requestId)` is unique and idempotent.
- Execution mutation uses `expectedRevision`; stale revision returns HTTP 409 with latest snapshot.
- Automatic conflict retry is at most once after reconcile; never loop indefinitely.
- Local pending action must be durably written before UI may hold a long-lived optimistic state.
- No formal QR/AirDrop join UI in this Task; Task 2 owns the polished join/role/takeover user flow. Task 1 must provide complete API, Store, Keychain, and testable role-selection data.
- Swift Core remains UI-free and network-free.
- All new Swift domain values must be `Sendable`; Codable values used for persistence/API must round-trip in tests.
- Use TDD for every task: failing test → verify failure → minimal implementation → verify green → full related suite → review → commit.
- After every Task, run `git diff --check` and request code review before proceeding.
